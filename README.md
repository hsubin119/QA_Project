# QA_Project

## 문제 1. 실시간 주문 현황 테스트 자동화 전략

### 1. 전략 수립의 전제

배달의민족 앱에 새롭게 추가되는 **실시간 주문 현황** 화면은 주문 접수부터 배달 완료까지의 상태를 사용자에게 실시간으로 전달하는 기능이라고 가정한다.

주요 주문 상태는 다음과 같다.

- 결제 완료
- 주문 접수 대기
- 주문 접수
- 조리 중
- 배달 준비 중
- 배달 중
- 배달 완료
- 주문 취소 또는 접수 거절

상태 변경은 서버 이벤트를 기준으로 발생하며, 클라이언트에는 WebSocket, Server-Sent Events 또는 Polling 방식으로 전달된다고 가정한다. 현재 자동화 테스트가 전혀 없고 개발 기간이 2주로 짧으므로, 모든 시나리오를 자동화하기보다 장애 영향도가 크고 반복 실행 가치가 높은 영역부터 자동화한다.

초기 자동화의 목표는 다음과 같다.

1. 주문 상태 전이 규칙의 정확성 검증
2. 서버와 앱 화면 간 상태 데이터 정합성 검증
3. 핵심 주문 흐름의 회귀 테스트 확보
4. 배포 전 빠른 피드백 제공
5. 이후 확장 가능한 자동화 기반 마련

---

### 1-1. 자동화 전략 수립

#### 자동화 여부 판단 기준

자동화 여부는 단순 반복 가능성만으로 결정하지 않고, **장애 영향도, 실행 빈도, 변경 빈도, 테스트 안정성, 데이터 준비 비용, 유지보수 비용**을 함께 고려한다.

자동화 우선순위가 높은 항목은 다음과 같다.

- 결함 발생 시 주문 경험이나 고객 신뢰에 큰 영향을 주는 기능
- 매 배포마다 반복 검증해야 하는 핵심 기능
- 입력과 기대 결과가 명확한 기능
- 여러 상태와 조건을 반복해서 검증해야 하는 기능
- API 또는 이벤트 수준에서 안정적으로 검증할 수 있는 기능
- 과거 장애가 발생했거나 장애 가능성이 높은 기능

다음 항목은 초기에는 수동 검증을 유지한다.

- 애니메이션의 자연스러움과 같은 정성적 품질
- 기기, OS, 네트워크 환경에 따른 체감 품질
- 요구사항이 자주 변경되는 UI
- 자동화 구현 비용에 비해 실행 빈도가 낮은 항목
- 실제 사용자 관점의 탐색적 테스트가 필요한 영역

#### 테스트 피라미드 기반 자동화 범위

초기 자동화 비중은 다음과 같이 구성한다.

| 레이어 | 비중 | 주요 목적 |
| --- | ---: | --- |
| API 및 서비스 | 약 65% | 상태 전이, 이벤트, 데이터 정합성 검증 |
| UI 컴포넌트 및 화면 | 약 25% | 상태별 표시와 주요 인터랙션 검증 |
| E2E | 약 10% | 고객에게 중요한 대표 흐름 검증 |

짧은 구축 기간에는 빠르고 실패 원인이 명확한 API 테스트로 넓은 범위를 확보하고, UI와 E2E 테스트는 핵심 흐름만 선별한다.

#### API 및 서비스 레이어 자동화

실시간 주문 현황 기능의 핵심은 서버가 올바른 상태를 생성하고 순서대로 전달하는 데 있으므로 API 및 서비스 레이어에 가장 많은 테스트를 배치한다.

**주문 현황 조회**

- 유효하거나 존재하지 않는 주문 ID 조회
- 다른 사용자의 주문 접근 차단
- 인증 토큰 누락 또는 만료 처리
- 주문 상태별 응답값과 필수 필드 검증
- 상태 변경 시간과 예상 도착 시간 형식 검증
- 주문 취소 또는 접수 거절 사유 검증

**주문 상태 전이**

- 정상 전이: 결제 완료 → 접수 대기 → 주문 접수 → 조리 중 → 배달 준비 중 → 배달 중 → 배달 완료
- 종료 상태의 역행 방지: 배달 완료 → 조리 중, 주문 취소 → 배달 중
- 동일 상태 이벤트 중복 수신
- 과거 이벤트가 뒤늦게 도착하는 경우
- 중간 상태가 누락된 이벤트
- 동일 주문에 상충하는 상태 변경이 동시에 발생하는 경우

**실시간 이벤트 처리**

- 서버 상태 변경 후 이벤트 발행 여부
- 이벤트의 주문 ID와 사용자 ID 정확성
- 이벤트 순서 보장과 중복 처리 방지
- 연결 종료 후 재연결 시 최신 상태 동기화
- 이벤트 유실 후 API 재조회에 의한 복구
- 여러 주문 이벤트의 주문별 분리 처리

**데이터 정합성**

- 주문 상세 API와 주문 현황 API의 상태 일치
- 이벤트 데이터와 조회 API 상태 일치
- 화면의 예상 시간과 서버 데이터 일치
- 취소 및 배달 완료 주문의 최종 상태 유지
- 타임스탬프와 상태 이력 순서 검증

API 또는 서비스 레이어에서는 상태를 직접 제어하거나 테스트 더블을 사용할 수 있어, UI에서 복잡한 주문 데이터를 준비하는 것보다 빠르고 안정적으로 다양한 조건을 검증할 수 있다.

#### UI 레이어 자동화

UI 자동화는 서버의 모든 비즈니스 규칙을 반복 검증하지 않고, 특정 상태가 주어졌을 때 화면이 올바르게 표현되는지에 집중한다. 서버 응답과 이벤트는 필요한 경우 Stub으로 제어한다.

- 주문 현황 화면 진입
- 상태에 맞는 제목, 안내 문구 및 Progress UI 표시
- 예상 배달 시간 노출
- 주문 취소 또는 접수 거절 상태 표시
- 새로고침 및 재시도 동작
- 네트워크 오류 안내
- 주문 상세 화면 이동
- 배달 완료 후 완료 화면 또는 리뷰 버튼 표시
- 앱 재실행 후 최신 상태 복원

예를 들어 `DELIVERING` 상태에서는 ‘배달 중’ 문구, 현재 단계, 완료된 이전 단계, 예상 도착 시간을 확인하고 주문 취소 버튼이 노출되지 않는지 검증한다.

다음 항목은 사람의 관찰과 탐색적 테스트가 더 효과적이므로 초기 자동화에서 제외한다.

- 상태 변경 애니메이션과 지도 이동의 시각적 품질
- 긴 가게명, 메뉴명, 주소의 레이아웃 품질
- 글자 크기 확대, 접근성 및 다크 모드 사용성
- 다양한 해상도와 저속 네트워크에서의 체감 품질
- 실제 푸시 알림 지연과 사용자 혼란 여부

#### E2E 자동화

E2E는 결제, 가게 시스템, 배차, 배달, 푸시 등 여러 시스템에 의존하므로 전체 테스트의 가장 작은 비중으로 유지한다.

**시나리오 1: 정상 주문 완료**

1. 주문을 완료하고 실시간 주문 현황 화면에 진입한다.
2. 접수 대기 상태를 확인한다.
3. 테스트 도구로 주문 상태를 변경한다.
4. 주문 접수, 조리 중, 배달 중 상태가 화면에 반영되는지 확인한다.
5. 최종적으로 배달 완료 상태를 확인한다.

**시나리오 2: 주문 접수 거절**

1. 주문 완료 후 가게에서 주문을 거절한다.
2. 화면에 거절 상태와 사유가 표시되는지 확인한다.
3. 결제 취소 또는 환불 안내가 표시되는지 확인한다.

**시나리오 3: 네트워크 단절 및 복구**

1. 주문 현황 화면에서 네트워크를 차단한다.
2. 서버에서 주문 상태를 변경한다.
3. 네트워크 복구 후 최신 상태로 동기화되는지 확인한다.

**시나리오 4: 앱 종료 후 상태 복원**

1. 주문 진행 중 앱을 종료한다.
2. 서버에서 주문 상태를 변경한다.
3. 앱을 다시 실행해 최신 상태가 노출되는지 확인한다.

실제 가게 단말기·라이더 앱 연동, 실결제 환불, 통신사별 푸시 지연, GPS 정확도 등 외부 의존성이 높은 영역은 안정적인 통합 테스트 환경이 마련되기 전까지 수동 또는 별도 통합 테스트로 검증한다.

#### 2주 스프린트 실행 계획

**1주 차**

- 요구사항과 주문 상태 전이표 정리
- API 계약 및 이벤트 스키마 검토
- 테스트 가능한 구조를 개발자와 협의
- API 테스트 프레임워크 구축
- 정상·예외 상태 전이 테스트 작성
- 테스트 데이터 생성 및 정리 방식 정의
- CI에서 API 테스트 실행

**2주 차**

- 상태별 UI 테스트 작성
- 정상 주문 흐름 E2E 1~2개 작성
- 네트워크 단절 및 복구 시나리오 검증
- 실패 로그, 스크린샷 및 영상 수집 설정
- Flaky 테스트 관리 정책 적용
- 배포 전 회귀 테스트 수행

오픈 전까지 핵심 API 자동화와 최소한의 Smoke E2E를 안정적으로 운영하는 것을 목표로 하고, 나머지는 오픈 이후 장애 이력과 변경 빈도를 바탕으로 확장한다.

#### 자동화 투자 대비 효과 판단

자동화 ROI는 테스트 케이스 수가 아니라 다음 요소로 평가한다.

- 반복 실행 빈도와 수동 테스트 소요 시간
- 자동화 구현 및 유지보수 시간
- 결함 발생 가능성과 고객·비즈니스 영향도
- 실행 안정성과 실패 원인 분석 가능성
- 여러 환경과 데이터에 대한 재사용성
- 배포 주기 단축 기여도

개념적으로 다음과 같이 판단할 수 있다.

> ROI = 절감된 수동 테스트 비용 + 조기 결함 발견 효과 + 장애 예방 효과 - 자동화 개발 및 유지보수 비용

주문 상태 전이 API 테스트는 빠르고 반복 실행이 쉬우며, 많은 상태 조합과 높은 장애 영향도를 다루므로 ROI가 높다. 반면 미세한 애니메이션을 좌표나 이미지 비교로 검증하는 테스트는 디자인 변경에 민감하고 유지보수 비용이 커 초기 ROI가 낮다.

도입 후에는 회귀 테스트 시간, 자동화 결함 발견 건수, 운영 회귀 결함, Pass 및 Flaky 비율, 평균 실행 시간, 유지보수 시간, 절감한 수동 검증 시간과 실패 분석 시간을 추적한다.

### 1-2. CI/CD 파이프라인 통합

#### Pull Request 단계

- 정적 분석, 단위 테스트, API 계약 테스트
- 핵심 상태 전이 API 테스트
- 변경 모듈과 관련된 UI 컴포넌트 테스트
- 목표 실행 시간 5~10분 이내
- 핵심 테스트 실패 시 Merge 차단

PR 단계에서는 빠른 피드백이 중요하므로 전체 E2E는 실행하지 않는다. 실패 결과에는 요청·응답, 기대값과 실제값 등 원인 분석에 필요한 정보를 포함한다.

#### 개발·통합 환경 배포 후

- 전체 API 회귀 테스트
- 이벤트 발행·구독 및 데이터 정합성 테스트
- 주요 UI 자동화
- 정상 주문, 주문 거절·취소, 네트워크 복구 E2E

핵심 Smoke 실패 시 다음 배포 단계로 진행하지 않는다. 비핵심 회귀 실패는 위험을 검토해 조건부 진행하며 QA와 담당 개발자에게 알린다. 로그, 스크린샷, 화면 녹화, API 요청·응답 및 테스트 데이터 ID를 결과에 첨부한다.

#### 정기 실행

매일 야간에 전체 API·UI·E2E 회귀, 여러 OS·기기 및 네트워크 조건, 장시간 연결 유지 테스트를 실행한다. 반복 실행 결과를 이용해 Flaky 발생률과 실패 추세도 관리한다.

#### Release Candidate 단계

운영과 유사한 환경에서 다음 핵심 항목을 필수 검증한다.

- 주문 상태 전이와 실시간 이벤트
- 정상 주문 및 주문 거절·취소 E2E
- 앱 종료 후 상태 복원
- 네트워크 재연결 후 최신 상태 복구
- 이전 버전과의 호환성

핵심 테스트 실패 시 운영 배포를 중단한다. 테스트 자체의 문제임이 명확한 경우에만 QA와 개발 책임자의 합의로 예외 처리한다.

#### 운영 배포 후

운영에 영향을 주지 않는 전용 계정과 격리된 데이터로 API Health Check, 인증·권한, 실시간 이벤트 연결, 주요 화면 진입 여부 등 최소 Smoke 테스트를 수행한다.

### Flaky 테스트 대응 정책

동일한 코드와 환경에서도 성공과 실패가 반복되는 테스트를 Flaky로 정의하며, 일반 테스트 실패와 분리해 관리한다.

#### 대응 절차

1. **증거 수집:** 실행 로그, 스크린샷, 영상, OS·앱·서버 버전, 주문 ID, API 요청·응답, 이벤트 시각, 네트워크 상태와 재시도 결과를 보존한다.
2. **분류:** 제품 결함, 테스트 코드, 데이터, 환경·인프라, 비동기 대기, 외부 시스템 의존성 또는 원인 미확인으로 구분한다.
3. **제한적 재시도:** 일시적인 네트워크·인프라 오류에만 최대 1회 허용한다. 재시도 성공도 `Flaky Pass`로 표시하고 최초 실패 기록을 남긴다. 명확한 Assertion 실패는 재시도하지 않는다.
4. **격리:** 최근 20회 중 2회 이상 비결정적으로 실패한 테스트는 후보로 등록하고 Quarantine Suite에서 계속 실행한다. 담당자와 수정 기한을 지정하며, 수정 후 연속 실행으로 안정성을 확인한다.

핵심 결제·주문 정합성 테스트는 Flaky라는 이유로 장기간 배포 차단 대상에서 제외하지 않는다. 원인을 우선 해결하거나 더 안정적인 하위 레이어 테스트로 대체한다.

#### 주요 원인 분석 순서

1. 고정 시간 대기 또는 불충분한 대기 조건
2. 테스트 데이터 충돌과 정리 실패
3. 테스트 간 실행 순서 의존성
4. 비동기 이벤트 처리 타이밍
5. 불안정한 UI Selector
6. 네트워크 및 테스트 환경 상태
7. 외부 시스템 의존성
8. 실제 제품의 Race Condition

실시간 상태 반영을 고정 `sleep`으로 기다리지 않고 특정 상태가 될 때까지 조건 기반으로 대기한다. 제한 시간이 초과되면 서버 상태와 이벤트 수신 기록을 함께 확인한다.

#### 예방 원칙

- 테스트별 독립 사용자와 주문 데이터 사용
- 시작 전 데이터 준비와 종료 후 정리
- 테스트 실행 순서에 대한 의존 제거
- 고정 대기 대신 조건 기반 대기 사용
- 텍스트·좌표 대신 안정적인 테스트 ID 사용
- 외부 시스템의 Stub 또는 Mock 격리
- 주문 ID와 이벤트 ID의 고유성 보장
- 병렬 실행 Namespace 분리

### 최종 전략 요약

2주라는 제한된 기간에는 전체 기능을 E2E로 자동화하지 않는다. 비즈니스 규칙과 상태 정합성은 API·서비스 레이어에서 폭넓게 검증하고, UI 레이어에서는 상태가 사용자에게 올바르게 표현되는지 확인한다. E2E는 정상 주문, 주문 거절, 네트워크 복구 등 고객에게 중요한 흐름만 자동화한다.

CI/CD에서는 빠른 API 테스트를 Pull Request 단계에서 실행하고, 통합 환경 배포 후 UI와 핵심 E2E를 실행한다. 전체 회귀는 정기 실행으로 분리해 개발 피드백 속도와 검증 범위의 균형을 맞춘다.

Flaky 테스트는 재시도로 숨기지 않고 증거 수집, 원인 분류, 제한적 재시도, 격리, 담당자 지정, 수정 후 안정성 확인 절차로 관리한다. 이를 통해 짧은 기간에도 핵심 주문 상태에 대한 신뢰도 높은 자동화 기반을 먼저 확보하고, 오픈 이후 실제 결함과 변경 이력을 기준으로 범위를 지속적으로 확장한다.

## 문제 2. B마트 재고 API 테스트 자동화

### 구현 범위

실제 서버 없이도 과제를 실행할 수 있도록 Python 표준 라이브러리의 `ThreadingHTTPServer`를 이용해 메모리 기반 Stub API를 구현했다.

| Method | Endpoint | 설명 |
| --- | --- | --- |
| `GET` | `/v1/products/{productId}/stock` | 현재 재고와 품절 여부 조회 |
| `POST` | `/v1/orders` | 결제 완료 주문 생성 및 재고 차감 |
| `POST` | `/v1/orders/{orderId}/cancel` | 주문 취소 및 재고 복구 |

주문 생성 요청 형식은 다음과 같이 정의했다.

```json
{
  "productId": "milk-1l",
  "quantity": 1
}
```

정상 주문은 `201 Created`, 재고 부족은 `409 Conflict`와 `OUT_OF_STOCK` 오류 코드를 반환한다. 존재하지 않는 상품·주문은 `404 Not Found`, 잘못된 수량은 `400 Bad Request`로 처리한다.

### 실행 방법

#### 사전 조건

- Python 3.11 이상
- 인터넷 연결은 최초 의존성 설치 시에만 필요

#### 설치

Windows PowerShell 기준:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

macOS 또는 Linux 기준:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

#### 전체 테스트 실행

```bash
python -m pytest -v
```

동시성 테스트만 실행하려면 다음 명령을 사용한다.

```bash
python -m pytest -v -k near_simultaneous
```

#### Stub 서버 단독 실행

```bash
python -m bmart_stock.server --port 8080 --product-id popular-product --stock 10
```

실행 후 별도 터미널에서 다음과 같이 호출할 수 있다.

```bash
curl http://127.0.0.1:8080/v1/products/popular-product/stock

curl -X POST http://127.0.0.1:8080/v1/orders \
  -H "Content-Type: application/json" \
  -d '{"productId":"popular-product","quantity":1}'
```

### 테스트 케이스

총 14개의 API 자동화 테스트를 구현했다.

1. 현재 재고 정상 조회
2. 존재하지 않는 상품 조회 실패
3. 반복 재고 조회 시 재고 미차감
4. 결제 완료 후 재고 1개 차감
5. 복수 수량 주문 후 재고 차감
6. 재고 부족 주문 거절 및 재고 보존
7. 수량 0 주문 유효성 검증
8. 존재하지 않는 상품 주문 실패
9. 주문 취소 후 차감 수량 복구
10. 존재하지 않는 주문 취소 실패
11. 중복 취소 방지 및 이중 복구 차단
12. 마지막 재고 주문 후 품절 전환
13. 품절 주문 취소 후 구매 가능 상태 복원
14. 마지막 재고 1개에 대한 동시 주문 시 1건 성공·1건 품절

### 동시성 테스트 설계

동시성 테스트는 재고가 1개인 상품을 준비하고 `ThreadPoolExecutor`의 작업 스레드 2개에서 주문을 전송한다. `Barrier`를 사용해 두 요청의 출발 시점을 맞춰 수십 ms 이내에 서버에 도달하도록 한다.

서버의 주문 처리에서는 다음 과정 전체를 하나의 `RLock` 임계 구역으로 묶었다.

1. 현재 재고 조회
2. 주문 수량과 재고 비교
3. 재고 차감
4. 주문 저장

따라서 두 요청이 동시에 처리되어도 첫 번째 요청만 재고를 1에서 0으로 변경할 수 있다. 테스트는 응답 코드가 정확히 `201` 1건과 `409` 1건인지, 실패 응답이 `OUT_OF_STOCK`인지, 최종 재고가 0이고 품절 상태인지 함께 검증한다. 단순히 스레드 실행이 끝났는지만 확인하지 않고 API 응답과 최종 상태를 모두 검증해 초과 판매 여부를 판단한다.

### 설계 의도

#### 실행 가능한 최소 Stub

과제의 초점은 웹 프레임워크 사용법보다 재고 규칙과 테스트 품질에 있다고 판단했다. 따라서 서버 구현은 Python 표준 라이브러리만 사용하고, 테스트 도구에 `pytest`와 `requests`만 추가했다. 별도 데이터베이스나 외부 서비스 없이 어느 환경에서도 빠르게 실행할 수 있다.

#### 도메인 로직과 HTTP 계층 분리

`InventoryStore`는 재고·주문 규칙과 동시성 제어를 담당하고, `StockApiHandler`는 URL·JSON·HTTP 상태 코드 변환만 담당한다. 이 구조는 도메인 정책을 HTTP 세부 구현과 분리해 규칙 변경 시 영향 범위를 줄인다.

#### 데이터 정합성 우선

재고 확인과 차감을 하나의 잠금 구간에서 수행해 Check-Then-Act Race Condition을 방지한다. 취소도 주문 상태 확인, 재고 복구, 주문 상태 변경을 원자적으로 수행한다. 이미 취소된 주문은 `409 ALREADY_CANCELLED`로 거절해 재고가 두 번 복구되는 문제를 막는다.

#### 명시적인 API 오류

실패 응답은 HTTP 상태 코드뿐 아니라 `PRODUCT_NOT_FOUND`, `OUT_OF_STOCK`, `ALREADY_CANCELLED`처럼 기계적으로 판별 가능한 오류 코드를 포함한다. 테스트가 자연어 메시지에 의존하지 않으므로 문구 변경에 덜 취약하다.

### 테스트 코드 구조

```text
.
├── bmart_stock/
│   ├── __init__.py
│   └── server.py
├── tests/
│   ├── conftest.py
│   ├── helpers.py
│   └── test_stock_api.py
├── pytest.ini
└── requirements.txt
```

- `bmart_stock/server.py`: 재고·주문 도메인 로직과 HTTP Stub 서버
- `tests/conftest.py`: 테스트별 독립 Store, 임의 포트 서버의 시작·종료, API Client fixture
- `tests/helpers.py`: HTTP 호출을 캡슐화한 Client와 재사용 가능한 재고·오류 검증 헬퍼
- `tests/test_stock_api.py`: 정상·예외·복구·품절·동시성 시나리오
- `pytest.ini`: 테스트 탐색 위치와 기본 출력 설정

각 테스트는 새로운 `InventoryStore`와 서버를 사용한다. 테스트 데이터가 다른 테스트에 남지 않으며 실행 순서와 병렬 실행 여부에 의존하지 않는다. 서버는 운영체제가 할당한 임의 포트에서 시작해 CI의 포트 충돌 가능성을 줄이고, fixture 종료 시 반드시 정리한다. 모든 HTTP 요청에는 2초 제한 시간을 적용해 서버 이상 시 테스트가 무한 대기하지 않도록 했다.

## 문제 3. E2E 자동화 코드 리뷰 및 리팩터링

### 기존 코드의 문제점

#### 안정성

1. `device.wait(...)`가 제한 시간 안에 객체를 찾지 못하면 `null`을 반환할 수 있지만, 곧바로 `click()`을 호출해 원인을 알기 어려운 NullPointerException이 발생한다.
2. `By.textContains("치킨")`, `By.textContains("결제")`처럼 부분 문자열에 의존해 같은 문구가 여러 곳에 있으면 엉뚱한 요소를 선택할 수 있다.
3. 화면 문구는 카피 변경, 다국어, A/B 테스트에 따라 바뀌므로 텍스트 Selector는 변경에 취약하다.
4. 각 화면이 실제로 전환되었는지 확인하지 않고 다음 요소를 찾는다. 이전 화면의 동일 문구나 늦게 사라지는 요소를 잘못 사용할 수 있다.
5. 요소가 보이는지만 확인하고 클릭 가능·활성화 상태인지 검증하지 않는다.
6. 결제 직후 `Thread.sleep(5000)`을 사용한다. 처리 속도가 빠르면 불필요하게 느리고, 5초보다 느리면 실패하는 고정 대기다.
7. 결제는 네트워크와 여러 백엔드 처리에 의존하지만 다른 화면과 동일한 짧은 제한 시간을 사용한다.
8. 테스트 데이터, 로그인 상태, 장바구니 초기화 및 주문 가능한 가게 상태가 명시되지 않아 이전 실행 결과에 의존한다.
9. 실제 결제·재고·가게 운영 상태를 공유하면 병렬 테스트끼리 충돌하거나 중복 주문이 발생할 수 있다.
10. 실패 시 스크린샷, 화면 계층, 로그, 주문 ID가 남지 않아 원인 분석이 어렵다.

#### 유지보수성

1. 화면 탐색, 동작, 대기, 검증이 하나의 테스트 메서드에 섞여 있다.
2. Selector와 제한 시간이 테스트 코드 곳곳에 하드코딩되어 변경 영향 범위가 크다.
3. 같은 흐름을 다른 테스트에서 재사용하기 어렵고 중복 코드가 증가한다.
4. `shopItem`, `menuItem` 등 UI 구현 세부사항이 테스트 의도를 가린다.
5. Page Object나 공통 대기·오류 처리 계층이 없어 화면 변경 시 모든 테스트를 수정해야 한다.
6. 테스트 이름 `testOrderFlow`만으로 어떤 주문 결과를 보장하는지 알기 어렵다.

#### 신뢰성

1. 최종 검증이 `Assert.assertNotNull(statusText)` 하나뿐이어서 올바른 주문의 상태인지 확인하지 않는다.
2. 주문 ID, 선택 메뉴, 결제 완료 여부를 검증하지 않아 이전 주문이나 다른 주문의 상태를 오인할 수 있다.
3. "접수 대기" 문구가 화면의 다른 안내 영역에 있어도 테스트가 통과할 수 있다.
4. 결제 오류 팝업이나 차단 오류가 함께 떠 있어도 상태 문구만 존재하면 통과한다.
5. 테스트 완료 후 생성 주문 정리 정책이 없어 후속 테스트와 운영 데이터에 영향을 줄 수 있다.
6. 사전조건 실패와 제품 결함을 구분하지 않아 테스트 결과의 의미가 불명확하다.

### 리팩터링 설계

코드는 다음 위치에 작성했다.

```text
problem3/e2e/src/androidTest/java/com/baemin/qa/
├── OrderFlowTest.kt
├── FailureArtifactsRule.kt
├── UiAutomatorSupport.kt
└── pages/
    └── OrderFlowPages.kt
```

#### Page Object

화면별 책임을 `ShopListPage`, `MenuPage`, `CartPage`, `PaymentPage`, `OrderStatusPage`로 분리했다. 테스트 본문은 "가게 선택 → 메뉴 선택 → 주문 → 결제 → 주문 상태 검증"이라는 업무 흐름만 표현한다.

각 Page Object는 다음 책임을 가진다.

- 화면 진입 완료 조건 정의
- 해당 화면의 안정적인 Selector 관리
- 사용자 동작 수행
- 다음 화면이 나타날 때까지 조건 기반 대기
- 화면에 특화된 검증 제공

#### Selector 전략

화면과 주요 동작은 `resource-id`를 기준으로 찾는다. 가게명과 메뉴명은 테스트 데이터 식별을 위해 정확한 텍스트를 사용하되, 각각 `shop_card`와 `menu_card` 내부의 자식 요소로 범위를 제한했다. 실제 앱 적용 시 개발팀과 협의해 자동화 전용 test tag 또는 안정적인 resource-id를 제공하는 것이 가장 좋다.

샘플의 `com.baemin.app` 패키지와 resource-id는 합리적으로 정의한 가상 명세이므로 실제 앱 ID에 맞게 교체해야 한다.

#### 대기 전략

- `Thread.sleep`을 제거하고 `Until.hasObject` 또는 `Until.findObject`로 필요한 상태가 될 때까지 기다린다.
- 일반 화면, 화면 전환, 결제 처리에 서로 다른 제한 시간을 사용한다.
- 요소를 찾지 못하면 기다린 대상과 제한 시간을 포함한 AssertionError를 발생시킨다.
- 실패 메시지에 현재 UI hierarchy를 포함해 CI에서도 실제 화면 상태를 확인할 수 있게 한다.
- 테스트 실패 시 `FailureArtifactsRule`이 스크린샷, UI hierarchy XML과 예외 Stack Trace를 자동 저장한다.
- 클릭 전 요소의 활성화 상태를 검사하고, 클릭 후에는 다음 화면의 고유 요소를 기다린다.

#### 검증 강화

리팩터링 테스트는 다음 결과를 함께 검증한다.

1. 장바구니에 정확한 메뉴가 담겼는지
2. 결제 후 주문 ID가 생성되었는지
3. 주문 현황 화면의 주문 ID가 방금 생성한 주문과 일치하는지
4. 주문 상태가 정확히 "접수 대기"인지
5. 결제 상태가 "결제 완료"인지
6. 차단 오류가 표시되지 않는지

단순 요소 존재 여부가 아니라 동일 주문에 대한 핵심 비즈니스 결과를 검증한다.

### 실행 방법

이 코드는 실제 Android 앱과 Gradle 프로젝트가 없는 과제 환경을 고려해 완성된 `androidTest` 코드 형태로 제공한다. 실제 프로젝트에서는 `problem3/e2e/src/androidTest` 아래 파일을 앱 모듈의 `src/androidTest`로 옮기고 다음 의존성을 사용한다.

```kotlin
androidTestImplementation("androidx.test.ext:junit:<project-version>")
androidTestImplementation("androidx.test:runner:<project-version>")
androidTestImplementation("androidx.test.uiautomator:uiautomator:<project-version>")
```

연결된 에뮬레이터 또는 테스트 기기에서 다음과 같이 실행한다.

```bash
./gradlew connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=com.baemin.qa.OrderFlowTest
```

Windows에서는 `gradlew.bat`을 사용한다.

```powershell
.\gradlew.bat connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=com.baemin.qa.OrderFlowTest
```

실행 전 CI fixture가 다음 조건을 보장해야 한다.

- 테스트 계정 로그인 완료
- "치킨 테스트 매장"이 영업 중이며 주문 가능
- "후라이드" 메뉴의 재고와 결제 수단 준비
- 이전 장바구니 및 팝업 제거
- 테스트 주문을 식별·취소할 수 있는 독립 데이터 제공
- 기기 애니메이션, 로케일, 네트워크 조건 고정

현재 저장소에는 Android 앱, Gradle Wrapper 및 실제 resource-id가 없으므로 계측 테스트를 여기서 직접 실행할 수는 없다. 이는 과제에서 허용한 조건이며, 실제 앱에 연결할 때 패키지명·Selector·fixture만 환경에 맞게 조정한다.

### CI Flaky 원인 추적 순서

#### 1. 실패 증거 보존

재시도 전에 최초 실패의 스크린샷, UI hierarchy, Logcat, 테스트·앱·서버 버전, 기기 정보, 네트워크 로그, 계정과 주문 ID를 저장한다. 재시도로 최초 실패 흔적을 덮어쓰지 않는다.

#### 2. 실패 지점과 유형 분류

마지막으로 성공한 Page Object 단계와 기다리던 조건을 기준으로 다음 중 하나로 분류한다.

- 제품 기능 결함
- Selector 또는 화면 구조 변경
- 잘못된 대기 조건
- 테스트 데이터·사전조건 문제
- 결제·주문 백엔드 또는 외부 의존성
- 에뮬레이터·네트워크·CI 인프라
- 테스트 코드 결함

#### 3. 동일 조건 재현

같은 앱 빌드, 계정, 기기 이미지, 로케일과 백엔드 버전으로 단독 재실행한다. 단독 실행은 통과하고 병렬 실행만 실패하면 공유 계정, 장바구니, 재고, 결제 수단 또는 주문 데이터 충돌을 우선 확인한다.

#### 4. 클라이언트와 서버 상태 대조

Order ID를 기준으로 앱 로그, 결제 응답, 주문 API 상태와 화면 표시를 시간순으로 대조한다.

- 서버 주문이 생성되지 않음: 결제·주문 API 또는 테스트 데이터 조사
- 서버는 접수 대기지만 UI가 갱신되지 않음: 이벤트 수신·상태 반영 제품 로직 조사
- 서버와 UI는 정상인데 요소를 못 찾음: Selector·화면 전환·대기 조건 조사
- 기기 자체가 멈춤: 리소스 부족, ANR, 에뮬레이터 상태 조사

#### 5. 타이밍과 Selector 검증

고정 대기 추가로 증상을 숨기지 않는다. 실제 완료 신호가 무엇인지 확인하고, 해당 상태를 기다리도록 조건을 수정한다. UI hierarchy에서 resource-id 중복·변경, 팝업 가림, 비활성 요소 선택 여부를 확인한다.

#### 6. 반복 실행으로 가설 검증

원인 후보를 수정한 후 동일 조건과 병렬 조건에서 반복 실행한다. 특정 기기·OS·시간대·부하에서만 발생하는지도 분리해 측정한다.

#### 7. 격리와 복구 기준

원인 분석 중인 Flaky 테스트는 별도 Quarantine Suite로 이동하되 삭제하지 않고 계속 실행한다. 주문 핵심 흐름이므로 담당자와 수정 기한을 지정한다. 수정 후 목표 횟수만큼 연속 통과하고 실패 증거가 사라졌을 때만 배포 차단 Suite로 복귀시킨다.

자동 재시도는 일시적 인프라 오류에 한해 최대 1회만 허용하고, 재시도 성공도 Flaky로 기록한다. Assertion 실패나 제품 상태 불일치는 재시도하지 않는다.
