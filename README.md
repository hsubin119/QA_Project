# QA_Project

## 문제 1. 실시간 주문 현황 테스트 자동화 전략

### 1. 전략 수립의 전제

**실시간 주문 현황** 화면은 주문 접수부터 배달 완료까지의 상태를 사용자에게 실시간으로 전달한다고 가정한다.

주요 주문 상태는 다음과 같다.

- 결제 완료
- 주문 접수 대기
- 주문 접수
- 조리 중
- 배달 준비 중
- 배달 중
- 배달 완료
- 주문 취소 또는 접수 거절

상태는 서버 이벤트를 기준으로 WebSocket, Server-Sent Events 또는 Polling으로 전달된다고 가정한다. 자동화가 없고 개발 기간이 2주이므로, 장애 영향과 반복 가치가 높은 영역부터 적용한다. 초기 목표는 상태 전이 규칙과 서버·화면 간 데이터 정합성을 검증하고, 핵심 회귀 테스트와 이후 확장 가능한 기반을 확보하는 것이다.

---

### 1-1. 자동화 전략 수립

#### 자동화 여부 판단 기준

자동화 여부는 **장애 영향도, 실행·변경 빈도, 안정성, 데이터 준비와 유지보수 비용**으로 판단한다.

반복 가능성만으로 대상을 정하지 않는다. 매 배포에서 자주 실행되고 기대 결과가 명확하더라도, 요구사항 변경으로 유지 비용이 과도하거나 환경 의존성 때문에 결과를 신뢰하기 어렵다면 하위 레이어로 옮기거나 수동 검증을 유지한다.

- 결함 발생 시 주문 경험이나 고객 신뢰에 큰 영향을 주는 기능
- 매 배포마다 반복 검증해야 하는 핵심 기능
- 기대 결과가 명확하고 여러 조건을 반복 검증하는 기능
- API·이벤트 수준에서 안정적으로 검증 가능하거나 장애 이력이 있는 기능

다음 항목은 수동으로 유지한다.

- 애니메이션의 자연스러움과 같은 정성적 품질
- 기기·OS·네트워크별 체감 품질과 접근성
- 변경이 잦거나 구현 비용 대비 실행 빈도가 낮은 UI

#### 테스트 피라미드 기반 자동화 범위

| 레이어 | 비중 | 주요 목적 |
| --- | ---: | --- |
| API 및 서비스 | 약 65% | 상태 전이, 이벤트, 데이터 정합성 검증 |
| UI 컴포넌트 및 화면 | 약 25% | 상태별 표시와 주요 인터랙션 검증 |
| E2E | 약 10% | 고객에게 중요한 대표 흐름 검증 |

API로 넓은 범위를 빠르게 확보하고 UI와 E2E는 핵심 흐름만 선별한다. 이 비중은 고정값이 아니라 초기 목표이며, 운영 장애와 변경 이력이 쌓이면 위험이 높은 영역을 중심으로 조정한다.

#### API 및 서비스 레이어 자동화

서버의 상태 생성·전달이 핵심이므로 API 및 서비스 레이어에 가장 많은 테스트를 배치한다.

**주문 현황 조회**

- 유효한 주문과 존재하지 않는 주문 조회
- 다른 사용자의 주문 접근 차단
- 인증 토큰 누락 또는 만료 처리
- 주문 상태별 응답값과 필수 필드 검증
- 상태 변경 시간과 예상 도착 시간 형식 검증
- 주문 취소 또는 접수 거절 사유 검증

**주문 상태 전이**

- 정상 전이: 결제 완료 → 접수 대기 → 주문 접수 → 조리 중 → 배달 준비 중 → 배달 중 → 배달 완료
- 종료 상태의 역행 방지: 배달 완료 → 조리 중, 주문 취소 → 배달 중
- 동일 상태 이벤트 중복 수신
- 과거 이벤트가 뒤늦게 도착하는 경우
- 중간 상태가 누락된 이벤트
- 동일 주문에 상충하는 상태 변경이 동시에 발생하는 경우

**실시간 이벤트 처리**

- 서버 상태 변경 후 이벤트 발행 여부
- 이벤트의 주문 ID와 사용자 ID 정확성
- 이벤트 순서 보장과 중복 처리 방지
- 연결 종료 후 재연결 시 최신 상태 동기화
- 이벤트 유실 후 API 재조회에 의한 복구
- 여러 주문 이벤트의 주문별 분리 처리

**데이터 정합성**

- 주문 상세 API, 주문 현황 API와 이벤트 상태 일치
- 화면 예상 시간과 서버 데이터 일치
- 취소 및 배달 완료 주문의 최종 상태 유지
- 타임스탬프와 상태 이력 순서 검증

상태 직접 제어와 테스트 더블을 활용해 UI보다 빠르고 안정적으로 검증한다. API 계약과 이벤트 스키마도 함께 확인해 서버가 올바른 값을 만들었지만 클라이언트가 해석하지 못하는 통합 결함을 조기에 찾는다.

#### UI 레이어 자동화

UI는 Stub으로 상태를 제어하고 화면 표현과 주요 인터랙션에 집중한다. 서버의 비즈니스 규칙을 UI에서 중복 검증하지 않아 실행 시간과 실패 원인 분석 비용을 줄인다.

- 주문 현황 화면 진입
- 상태에 맞는 제목, 안내 문구와 Progress UI 표시
- 예상 배달 시간 노출
- 주문 취소·접수 거절·네트워크 오류 표시
- 새로고침, 재시도와 주문 상세 화면 이동
- 배달 완료 화면과 리뷰 버튼 표시
- 앱 재실행 후 최신 상태 복원

예를 들어 `DELIVERING`에서는 ‘배달 중’ 문구, 현재 단계, 완료된 이전 단계, 예상 도착 시간과 주문 취소 버튼 미노출을 검증한다.

사람의 판단이 효과적인 다음 항목은 자동화에서 제외한다.

- 상태 변경 애니메이션과 지도 이동의 시각적 품질
- 긴 텍스트, 접근성, 다크 모드와 다양한 해상도의 레이아웃
- 저속 네트워크, 실제 푸시 지연과 사용자 체감

#### E2E 자동화

E2E는 결제, 가게 시스템, 배차와 배달 등 외부 의존성이 높으므로 고객 영향이 큰 대표 흐름만 유지한다. 각 시나리오는 독립된 계정과 주문 데이터를 사용하고 실행 후 데이터를 정리한다.

**시나리오 1: 정상 주문 완료**

1. 주문을 완료하고 실시간 주문 현황 화면에 진입한다.
2. 접수 대기 상태를 확인한다.
3. 테스트 도구로 주문 상태를 변경한다.
4. 주문 접수, 조리 중, 배달 중 상태의 화면 반영을 확인한다.
5. 최종 배달 완료 상태를 확인한다.

**시나리오 2: 주문 접수 거절**

1. 주문 완료 후 가게에서 주문을 거절한다.
2. 화면의 거절 상태와 사유를 확인한다.
3. 결제 취소 또는 환불 안내를 확인한다.

**시나리오 3: 네트워크 단절 및 복구**

1. 주문 현황 화면에서 네트워크를 차단한다.
2. 서버의 주문 상태를 변경한다.
3. 네트워크 복구 후 최신 상태 동기화를 확인한다.

**시나리오 4: 앱 종료 후 상태 복원**

1. 주문 진행 중 앱을 종료한다.
2. 서버에서 주문 상태를 변경한다.
3. 앱 재실행 후 최신 상태를 확인한다.

실단말·라이더 앱, 실결제, 통신사 푸시와 GPS는 통합 환경이 마련되기 전까지 별도로 검증한다.

#### 2주 스프린트 실행 계획

**1주 차**

- 요구사항과 주문 상태 전이표 정리
- API 계약 및 이벤트 스키마 검토
- 테스트 가능한 구조와 데이터 준비·정리 방식 협의
- API 프레임워크와 정상·예외 상태 전이 테스트 구축
- CI에서 API 테스트 실행

**2주 차**

- 상태별 UI 테스트 작성
- 정상 주문 흐름 E2E 1~2개 작성
- 네트워크 단절·복구 시나리오 검증
- 실패 로그, 스크린샷과 영상 수집 설정
- Flaky 정책 적용 및 배포 전 회귀 테스트

오픈 전에는 핵심 API와 Smoke E2E를 확보하고 이후 장애·변경 이력에 따라 확장한다.

#### 자동화 투자 대비 효과 판단

ROI는 테스트 수가 아니라 다음 요소로 평가한다. 자동화 도입 전후의 회귀 시간과 운영 결함을 비교하고, 유지보수에 드는 시간까지 포함해 지속 여부를 결정한다.

- 반복 실행 빈도와 수동 테스트 소요 시간
- 구현·유지보수 시간
- 결함 발생 가능성과 고객·비즈니스 영향도
- 안정성, 원인 분석 가능성, 재사용성
- 배포 주기 단축 기여도

> ROI = 절감된 수동 테스트 비용 + 조기 결함 발견 효과 + 장애 예방 효과 - 자동화 개발 및 유지보수 비용

상태 전이 API는 빠르고 장애 영향이 커 ROI가 높지만, 미세한 애니메이션 비교는 변경에 민감해 초기 ROI가 낮다.

도입 후 회귀 시간, 결함 발견, 운영 회귀 결함, Flaky 비율, 유지보수·실패 분석 시간을 추적한다.

### 1-2. CI/CD 파이프라인 통합

#### Pull Request 단계

- 정적 분석, 단위 테스트, API 계약 테스트
- 핵심 상태 전이 API 테스트
- 변경 모듈과 관련된 UI 컴포넌트 테스트
- 목표 실행 시간 5~10분 이내
- 핵심 테스트 실패 시 Merge 차단

PR 단계에서는 빠른 피드백을 위해 전체 E2E는 제외한다. 실패 결과에는 요청·응답, 기대값과 실제값을 포함해 담당자가 재실행 전에 원인을 판단할 수 있게 한다.

#### 개발·통합 환경 배포 후

- 전체 API 회귀 테스트
- 이벤트 발행·구독 및 데이터 정합성 테스트
- 주요 UI 자동화
- 정상 주문, 주문 거절·취소, 네트워크 복구 E2E

핵심 Smoke 실패는 배포를 차단한다. 비핵심 실패는 위험을 검토하며, 결과에 로그·스크린샷·API 요청·응답과 데이터 ID를 첨부한다.

#### 정기 실행

야간에 전체 회귀와 OS·기기·네트워크·장시간 연결 테스트를 실행하고 Flaky 추세를 관리한다.

#### Release Candidate 단계

- 주문 상태 전이와 실시간 이벤트
- 정상 주문 및 주문 거절·취소 E2E
- 앱 종료 후 상태 복원
- 네트워크 재연결 후 최신 상태 복구
- 이전 버전과의 호환성

핵심 실패는 배포를 중단하며 테스트 문제로 확인된 경우에만 합의로 예외 처리한다.

#### 운영 배포 후

운영에 영향을 주지 않는 전용 계정과 격리된 데이터로 API Health Check, 인증·권한, 실시간 이벤트 연결, 주요 화면 진입 여부 등 최소 Smoke 테스트를 수행한다.

### Flaky 테스트 대응 정책

동일 코드·환경에서 성공과 실패가 반복되는 테스트를 Flaky로 정의한다.

#### 대응 절차

1. **증거 수집:** 실행 로그, 스크린샷, 영상, OS·앱·서버 버전, 주문 ID, API 요청·응답, 이벤트 시각, 네트워크 상태와 재시도 결과를 보존한다.
2. **분류:** 제품 결함, 테스트 코드, 데이터, 환경·인프라, 비동기 대기, 외부 시스템 의존성 또는 원인 미확인으로 구분한다.
3. **제한적 재시도:** 일시적인 네트워크·인프라 오류에만 최대 1회 허용한다. 재시도 성공도 `Flaky Pass`로 표시하고 최초 실패 기록을 남긴다. 명확한 Assertion 실패는 재시도하지 않는다.
4. **격리:** 최근 20회 중 2회 이상 비결정적으로 실패한 테스트는 후보로 등록하고 Quarantine Suite에서 계속 실행한다. 담당자와 수정 기한을 지정하며, 수정 후 연속 실행으로 안정성을 확인한다.

핵심 결제·주문 테스트는 Flaky라는 이유로 장기 격리하지 않고 우선 수정하거나 하위 레이어로 대체한다.

#### 주요 원인 분석 순서

1. 고정 시간 대기 또는 불충분한 대기 조건
2. 테스트 데이터 충돌과 정리 실패
3. 테스트 간 실행 순서 의존성
4. 비동기 이벤트 처리 타이밍
5. 불안정한 UI Selector
6. 네트워크 및 테스트 환경 상태
7. 외부 시스템 의존성
8. 실제 제품의 Race Condition

고정 `sleep` 대신 상태 기반으로 대기하고, Timeout 시 서버 상태와 이벤트 기록을 확인한다.

#### 예방 원칙

- 테스트별 독립 사용자와 주문 데이터 사용
- 시작 전 데이터 준비와 종료 후 정리
- 테스트 실행 순서에 대한 의존 제거
- 고정 대기 대신 조건 기반 대기 사용
- 텍스트·좌표 대신 안정적인 테스트 ID 사용
- 외부 시스템의 Stub 또는 Mock 격리

## 문제 2. B마트 재고 API 테스트 자동화

### 구현 범위

실제 서버 없이도 과제를 실행할 수 있도록 Python 표준 라이브러리의 `ThreadingHTTPServer`를 이용해 메모리 기반 Stub API를 구현했다.

| Method | Endpoint | 설명 |
| --- | --- | --- |
| `GET` | `/v1/products/{productId}/stock` | 현재 재고와 품절 여부 조회 |
| `POST` | `/v1/orders` | 결제 완료 주문 생성 및 재고 차감 |
| `POST` | `/v1/orders/{orderId}/cancel` | 주문 취소 및 재고 복구 |

주문 생성 요청 형식은 다음과 같이 정의했다.

```json
{
  "productId": "milk-1l",
  "quantity": 1
}
```

정상 주문은 `201 Created`, 재고 부족은 `409 Conflict`와 `OUT_OF_STOCK` 오류 코드를 반환한다. 존재하지 않는 상품·주문은 `404 Not Found`, 잘못된 수량은 `400 Bad Request`로 처리한다.

운영자 수동 재고 수정과 다른 탭의 실시간 이벤트 반영은 제공된 API 명세에 포함되지 않아 이번 프로토타입에서 제외했다. 실제 관리·이벤트 API가 제공되면 통합 테스트로 확장한다.

### 실행 방법

### 테스트 케이스

총 14개의 API 자동화 테스트를 구현했다.

1. 현재 재고 정상 조회
2. 존재하지 않는 상품 조회 실패
3. 반복 재고 조회 시 재고 미차감
4. 결제 완료 후 재고 1개 차감
5. 복수 수량 주문 후 재고 차감
6. 재고 부족 주문 거절 및 재고 보존
7. 수량 0 주문 유효성 검증
8. 존재하지 않는 상품 주문 실패
9. 주문 취소 후 차감 수량 복구
10. 존재하지 않는 주문 취소 실패
11. 중복 취소 방지 및 이중 복구 차단
12. 마지막 재고 주문 후 품절 전환
13. 품절 주문 취소 후 구매 가능 상태 복원
14. 마지막 재고 1개에 대한 동시 주문 시 1건 성공·1건 품절

### 동시성 테스트 설계

동시성 테스트는 재고가 1개인 상품을 준비하고 `ThreadPoolExecutor`의 작업 스레드 2개에서 주문을 전송한다. `Barrier`로 시작점을 맞춘 뒤 한 요청을 20ms 지연시키며, 실제 요청 시작 간격이 15~100ms인지 검증한다.

서버의 주문 처리에서는 다음 과정 전체를 하나의 `RLock` 임계 구역으로 묶었다.

1. 현재 재고 조회
2. 주문 수량과 재고 비교
3. 재고 차감
4. 주문 저장

따라서 두 요청이 동시에 처리되어도 첫 번째 요청만 재고를 1에서 0으로 변경할 수 있다. 테스트는 응답 코드가 정확히 `201` 1건과 `409` 1건인지, 실패 응답이 `OUT_OF_STOCK`인지, 최종 재고가 0이고 품절 상태인지 함께 검증한다. 단순히 스레드 실행이 끝났는지만 확인하지 않고 API 응답과 최종 상태를 모두 검증해 초과 판매 여부를 판단한다.

### 설계 의도

#### 실행 가능한 최소 Stub

과제의 초점은 웹 프레임워크 사용법보다 재고 규칙과 테스트 품질에 있다고 판단했다. 따라서 서버 구현은 Python 표준 라이브러리만 사용하고, 테스트 도구에 `pytest`와 `requests`만 추가했다. 별도 데이터베이스나 외부 서비스 없이 어느 환경에서도 빠르게 실행할 수 있다.

#### 도메인 로직과 HTTP 계층 분리

`InventoryStore`는 재고·주문 규칙과 동시성 제어를 담당하고, `StockApiHandler`는 URL·JSON·HTTP 상태 코드 변환만 담당한다. 이 구조는 도메인 정책을 HTTP 세부 구현과 분리해 규칙 변경 시 영향 범위를 줄인다.

#### 데이터 정합성 우선

재고 확인과 차감을 하나의 잠금 구간에서 수행해 Check-Then-Act Race Condition을 방지한다. 취소도 주문 상태 확인, 재고 복구, 주문 상태 변경을 원자적으로 수행한다. 이미 취소된 주문은 `409 ALREADY_CANCELLED`로 거절해 재고가 두 번 복구되는 문제를 막는다.

#### 명시적인 API 오류

실패 응답은 HTTP 상태 코드뿐 아니라 `PRODUCT_NOT_FOUND`, `OUT_OF_STOCK`, `ALREADY_CANCELLED`처럼 기계적으로 판별 가능한 오류 코드를 포함한다. 테스트가 자연어 메시지에 의존하지 않으므로 문구 변경에 덜 취약하다.

## 문제 3. E2E 자동화 코드 리뷰 및 리팩터링

### 기존 코드의 문제점

#### 안정성

1. `device.wait(...)`가 제한 시간 안에 객체를 찾지 못하면 `null`을 반환할 수 있지만, 곧바로 `click()`을 호출해 원인을 알기 어려운 NullPointerException이 발생한다.
2. `By.textContains("치킨")`, `By.textContains("결제")`처럼 부분 문자열에 의존해 같은 문구가 여러 곳에 있으면 엉뚱한 요소를 선택할 수 있다.
3. 화면 문구는 카피 변경, 다국어, A/B 테스트에 따라 바뀌므로 텍스트 Selector는 변경에 취약하다.
4. 각 화면이 실제로 전환되었는지 확인하지 않고 다음 요소를 찾는다. 이전 화면의 동일 문구나 늦게 사라지는 요소를 잘못 사용할 수 있다.
5. 요소가 보이는지만 확인하고 클릭 가능·활성화 상태인지 검증하지 않는다.
6. 결제 직후 `Thread.sleep(5000)`을 사용한다. 처리 속도가 빠르면 불필요하게 느리고, 5초보다 느리면 실패하는 고정 대기다.
7. 결제는 네트워크와 여러 백엔드 처리에 의존하지만 다른 화면과 동일한 짧은 제한 시간을 사용한다.
8. 테스트 데이터, 로그인 상태, 장바구니 초기화 및 주문 가능한 가게 상태가 명시되지 않아 이전 실행 결과에 의존한다.
9. 실제 결제·재고·가게 운영 상태를 공유하면 병렬 테스트끼리 충돌하거나 중복 주문이 발생할 수 있다.
10. 실패 시 스크린샷, 화면 계층, 로그, 주문 ID가 남지 않아 원인 분석이 어렵다.

#### 유지보수성

1. 화면 탐색, 동작, 대기, 검증이 하나의 테스트 메서드에 섞여 있다.
2. Selector와 제한 시간이 테스트 코드 곳곳에 하드코딩되어 변경 영향 범위가 크다.
3. 같은 흐름을 다른 테스트에서 재사용하기 어렵고 중복 코드가 증가한다.
4. `shopItem`, `menuItem` 등 UI 구현 세부사항이 테스트 의도를 가린다.
5. Page Object나 공통 대기·오류 처리 계층이 없어 화면 변경 시 모든 테스트를 수정해야 한다.
6. 테스트 이름 `testOrderFlow`만으로 어떤 주문 결과를 보장하는지 알기 어렵다.

#### 신뢰성

1. 최종 검증이 `Assert.assertNotNull(statusText)` 하나뿐이어서 올바른 주문의 상태인지 확인하지 않는다.
2. 주문 ID, 선택 메뉴, 결제 완료 여부를 검증하지 않아 이전 주문이나 다른 주문의 상태를 오인할 수 있다.
3. "접수 대기" 문구가 화면의 다른 안내 영역에 있어도 테스트가 통과할 수 있다.
4. 결제 오류 팝업이나 차단 오류가 함께 떠 있어도 상태 문구만 존재하면 통과한다.
5. 테스트 완료 후 생성 주문 정리 정책이 없어 후속 테스트와 운영 데이터에 영향을 줄 수 있다.
6. 사전조건 실패와 제품 결함을 구분하지 않아 테스트 결과의 의미가 불명확하다.

### 리팩터링 설계

코드는 다음 위치에 작성했다.

```text
problem3/e2e/src/androidTest/java/com/baemin/qa/
├── OrderFlowTest.kt
├── FailureArtifactsRule.kt
├── TestDataApi.kt
├── UiAutomatorSupport.kt
└── pages/
    └── OrderFlowPages.kt
```

#### Page Object

화면별 책임을 `ShopListPage`, `MenuPage`, `CartPage`, `PaymentPage`, `OrderStatusPage`로 분리했다. 테스트 본문은 "가게 선택 → 메뉴 선택 → 주문 → 결제 → 주문 상태 검증"이라는 업무 흐름만 표현한다.

각 Page Object는 다음 책임을 가진다.

- 화면 진입 완료 조건 정의
- 해당 화면의 안정적인 Selector 관리
- 사용자 동작 수행
- 다음 화면이 나타날 때까지 조건 기반 대기
- 화면에 특화된 검증 제공

#### Selector 전략

화면과 주요 동작은 `resource-id`를 기준으로 찾는다. 가게명과 메뉴명은 테스트 데이터 식별을 위해 정확한 텍스트를 사용하되, 각각 `shop_card`와 `menu_card` 내부의 자식 요소로 범위를 제한했다. 실제 앱 적용 시 개발팀과 협의해 자동화 전용 test tag 또는 안정적인 resource-id를 제공하는 것이 가장 좋다.

샘플의 `com.baemin.app` 패키지와 resource-id는 합리적으로 정의한 가상 명세이므로 실제 앱 ID에 맞게 교체해야 한다.

#### 대기 전략

- `Thread.sleep`을 제거하고 `Until.hasObject` 또는 `Until.findObject`로 필요한 상태가 될 때까지 기다린다.
- 일반 화면, 화면 전환, 결제 처리에 서로 다른 제한 시간을 사용한다.
- 요소를 찾지 못하면 기다린 대상과 제한 시간을 포함한 AssertionError를 발생시킨다.
- 실패 메시지에 현재 UI hierarchy를 포함해 CI에서도 실제 화면 상태를 확인할 수 있게 한다.
- 테스트 실패 시 `FailureArtifactsRule`이 스크린샷, UI hierarchy XML과 예외 Stack Trace를 자동 저장한다.
- 클릭 전 요소의 활성화 상태를 검사하고, 클릭 후에는 다음 화면의 고유 요소를 기다린다.

#### 검증 강화

리팩터링 테스트는 다음 결과를 함께 검증한다.

1. 장바구니에 정확한 메뉴가 담겼는지
2. 결제 후 주문 ID가 생성되었는지
3. 주문 현황 화면의 주문 ID가 방금 생성한 주문과 일치하는지
4. 주문 상태가 정확히 "접수 대기"인지
5. 결제 상태가 "결제 완료"인지
6. 차단 오류가 표시되지 않는지

단순 요소 존재 여부가 아니라 동일 주문에 대한 핵심 비즈니스 결과를 검증한다.

### 실행 방법

본 코드는 실제 앱이 제공되지 않은 과제 환경을 고려해 완성된 `androidTest` 형태로 작성했다. 실제 프로젝트에서는 파일을 앱 모듈의 `src/androidTest`에 배치하고 UIAutomator 의존성을 추가한 뒤 실행한다. 테스트 전에는 장바구니를 초기화하고, 종료 후에는 생성한 주문을 취소한 뒤 장바구니를 다시 비운다.

```bash
./gradlew connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=com.baemin.qa.OrderFlowTest \
  -Pandroid.testInstrumentationRunnerArguments.testDataApiUrl=<test-support-url> \
  -Pandroid.testInstrumentationRunnerArguments.testDataApiToken=<test-support-token>
```

테스트 환경은 `DELETE /test-support/cart`와 `DELETE /test-support/orders/{orderId}`를 제공한다고 가정한다. 로그인된 테스트 계정, 주문 가능한 테스트 매장·메뉴, 안정적인 resource-id도 필요하다. 현재 저장소에는 Android 앱, Gradle Wrapper와 실제 API가 없으므로 계측 테스트 실행은 생략했다.

### CI Flaky 원인 추적 순서

#### 1. 실패 증거 보존

재시도 전에 최초 실패의 스크린샷, UI hierarchy, Logcat, 테스트·앱·서버 버전, 기기 정보, 네트워크 로그, 계정과 주문 ID를 저장한다. 재시도로 최초 실패 흔적을 덮어쓰지 않는다.

#### 2. 실패 지점과 유형 분류

마지막으로 성공한 Page Object 단계와 기다리던 조건을 기준으로 다음 중 하나로 분류한다.

- 제품 기능 결함
- Selector 또는 화면 구조 변경
- 잘못된 대기 조건
- 테스트 데이터·사전조건 문제
- 결제·주문 백엔드 또는 외부 의존성
- 에뮬레이터·네트워크·CI 인프라
- 테스트 코드 결함

#### 3. 동일 조건 재현

같은 앱 빌드, 계정, 기기 이미지, 로케일과 백엔드 버전으로 단독 재실행한다. 단독 실행은 통과하고 병렬 실행만 실패하면 공유 계정, 장바구니, 재고, 결제 수단 또는 주문 데이터 충돌을 우선 확인한다.

#### 4. 클라이언트와 서버 상태 대조

Order ID를 기준으로 앱 로그, 결제 응답, 주문 API 상태와 화면 표시를 시간순으로 대조한다.

- 서버 주문이 생성되지 않음: 결제·주문 API 또는 테스트 데이터 조사
- 서버는 접수 대기지만 UI가 갱신되지 않음: 이벤트 수신·상태 반영 제품 로직 조사
- 서버와 UI는 정상인데 요소를 못 찾음: Selector·화면 전환·대기 조건 조사
- 기기 자체가 멈춤: 리소스 부족, ANR, 에뮬레이터 상태 조사

#### 5. 타이밍과 Selector 검증

고정 대기 추가로 증상을 숨기지 않는다. 실제 완료 신호가 무엇인지 확인하고, 해당 상태를 기다리도록 조건을 수정한다. UI hierarchy에서 resource-id 중복·변경, 팝업 가림, 비활성 요소 선택 여부를 확인한다.

#### 6. 반복 실행으로 가설 검증

원인 후보를 수정한 후 동일 조건과 병렬 조건에서 반복 실행한다. 특정 기기·OS·시간대·부하에서만 발생하는지도 분리해 측정한다.

#### 7. 격리와 복구 기준

원인 분석 중인 Flaky 테스트는 별도 Quarantine Suite로 이동하되 삭제하지 않고 계속 실행한다. 주문 핵심 흐름이므로 담당자와 수정 기한을 지정한다. 수정 후 목표 횟수만큼 연속 통과하고 실패 증거가 사라졌을 때만 배포 차단 Suite로 복귀시킨다.

자동 재시도는 일시적 인프라 오류에 한해 최대 1회만 허용하고, 재시도 성공도 Flaky로 기록한다. Assertion 실패나 제품 상태 불일치는 재시도하지 않는다.

### 문제 3에서 사용한 도구

#### Codex

OpenAI Codex를 다음 작업에 활용했다.

- 과제 PDF의 문제 3 요구사항 재확인
- 기존 UIAutomator 코드의 안정성·유지보수성·신뢰성 문제 분석
- Page Object와 공통 조건 기반 대기 유틸리티 설계
- 주문 ID·결제 상태·오류 상태를 포함한 검증 강화
- CI Flaky 원인 추적 절차와 실행 전제 문서화
- 코드 구조와 Git 변경 범위 검토

AI가 제안한 Selector와 앱 패키지는 가상 명세이며, 실제 프로젝트 적용 시 개발팀이 제공하는 resource-id와 테스트 데이터 정책에 맞춰 검증·수정해야 한다.

## 문제 4. 운영 장애 기반 회귀 테스트 자동 생성

### 아이디어 개요

`Incident-to-Test Generator`는 운영 장애의 보고서, 로그, 장애 타임라인과 재발 방지 대책을 AI/LLM으로 분석하여 재현 가능한 회귀 테스트 초안을 생성하는 도구다.

장애가 복구된 뒤 회귀 테스트 작성이 누락되거나 복합적인 장애 조건 중 일부만 테스트에 반영되는 문제를 줄이는 것이 목적이다. 실제 고객에게 영향을 준 장애를 자동화 우선순위에 반영하여 장애 문서를 지속적으로 실행 가능한 테스트 자산으로 전환한다.

### 해결하려는 문제

- 장애 보고서가 문서로만 남고 자동화 테스트로 연결되지 않음
- 담당자마다 장애 재현과 테스트 설계 수준이 다름
- 수정 코드만 검증하고 인접한 위험 조건을 놓침
- 시간이 지나며 장애의 원인과 재현 방법이 사라짐
- 같은 유형의 장애가 다른 서비스에서 반복됨

### 동작 구조

```text
운영 장애 발생
      │
      ▼
1. 장애 자료 수집
   - 보고서, 로그, API 요청·응답, 타임라인
      │
      ▼
2. 개인정보·Secret 제거
      │
      ▼
3. 장애 정보 구조화
   - 사전조건, Trigger, 기대·실제 결과, 근본 원인
      │
      ▼
4. 재현 가능성과 적절한 테스트 레이어 판단
      │
      ▼
5. 회귀 시나리오 및 코드 초안 생성
      │
      ▼
6. 격리 환경 검증
   - 수정 전 실패, 수정 후 성공
      │
      ▼
7. QA 리뷰 후 회귀 Suite 등록
```

### 적용 예시

재고가 1개 남은 상품에 고객 A와 B가 동시에 주문해 두 주문이 모두 성공하고 재고가 -1이 된 장애를 가정한다. 근본 원인은 재고 확인과 차감이 하나의 트랜잭션으로 처리되지 않은 Race Condition이다.

도구는 다음 테스트를 생성한다.

1. 재고 1개에 두 주문이 동시에 요청되면 1건만 성공
2. 나머지 주문은 `OUT_OF_STOCK`으로 실패
3. 최종 재고는 0이며 음수가 되지 않음
4. 성공 주문 취소 후 재고가 1로 복구
5. 실패 주문 취소 요청 시 재고가 변경되지 않음

단일 장애의 재현 테스트뿐 아니라 같은 원인에서 파생되는 경계값과 예외 시나리오도 추천한다.

### 테스트 생성 원칙

#### 장애 재현

생성된 테스트는 수정 전 버전에서 실제 장애를 재현해 실패해야 한다. 수정 전에도 성공한다면 장애 조건을 제대로 표현하지 못한 테스트다.

#### 수정 검증

수정된 버전에서는 같은 테스트가 성공해야 한다.

```text
수정 전 코드 + 생성 테스트 → 실패
수정 후 코드 + 생성 테스트 → 성공
```

#### 적절한 테스트 레이어

모든 장애를 E2E로 생성하지 않는다.

| 장애 원인 | 권장 테스트 레이어 |
| --- | --- |
| 상태 전이 규칙 | Unit 또는 API |
| 데이터 정합성 | API 또는 통합 |
| 동시성·트랜잭션 | 서비스 또는 통합 |
| 화면 표시 | UI Component |
| 주요 사용자 흐름 | E2E |
| 외부 시스템 장애 | Contract 또는 Fault Injection |
| 대량 트래픽 | Performance |

장애 원인을 가장 낮고 안정적인 레이어에서 검증하고, 고객 영향이 큰 대표 흐름만 E2E로 추가한다.

### 프로토타입 구조

```text
problem4/
├── __init__.py
├── incident_to_test.py
└── examples/
    └── incident.json

tests/
└── test_incident_to_test.py
```

- `incident_to_test.py`: 장애 입력 검증과 회귀 테스트 초안 생성
- `incident.json`: 재고 Race Condition 장애 샘플
- `test_incident_to_test.py`: 정보 누락, 미확정·미지원 원인과 생성 결과 검증

프로토타입은 근본 원인이 확정된 `RACE_CONDITION` 장애만 실제 테스트 시나리오로 변환한다. 다른 장애 유형은 추측하여 생성하지 않고 `REVIEW_REQUIRED`로 반환한다.

### 실행 방법

저장소 루트에서 샘플 장애를 변환한다.

```bash
python -m problem4.incident_to_test problem4/examples/incident.json
```

문제 4 테스트만 실행한다.

```bash
python -m pytest -v tests/test_incident_to_test.py
```

전체 회귀 테스트를 실행한다.

```bash
python -m pytest -v
```

실행 결과는 `DRAFT_CREATED` 또는 `REVIEW_REQUIRED` 상태와 테스트 시나리오를 JSON으로 출력한다. 생성 결과는 자동으로 회귀 Suite에 등록하지 않고 QA 검토를 거친다.

### LLM 프롬프트 설계

```text
역할:
당신은 운영 장애의 재발을 방지하는 Senior QA Engineer입니다.

목표:
장애 보고서에서 재현 조건, 기대 결과, 실제 결과와 근본 원인을
추출하고 적절한 회귀 테스트를 제안하세요.

원칙:
1. 장애 보고서에 없는 사실을 임의로 만들지 마세요.
2. 근본 원인이 확정되지 않았다면 테스트 코드를 생성하지 마세요.
3. 사용자 영향과 근본 원인을 구분하세요.
4. 가장 낮고 안정적인 테스트 레이어를 우선 추천하세요.
5. 모든 시나리오를 E2E로 만들지 마세요.
6. 수정 전 실패하고 수정 후 성공하는 테스트를 설계하세요.
7. 운영 URL, 계정, 개인정보와 Secret을 사용하지 마세요.
8. 테스트는 독립적이고 반복 실행 가능해야 합니다.
9. 생성 결과는 QA 검토 전까지 초안으로 표시하세요.

입력:
- 장애 보고서: {{incident_report}}
- 정제된 장애 로그: {{sanitized_logs}}
- API 명세: {{api_spec}}
- 수정 코드 Diff: {{fix_diff}}
- 기존 테스트: {{existing_tests}}
- 유사 장애: {{similar_incidents}}

출력:
{
  "incidentSummary": "",
  "rootCauseConfirmed": true,
  "preconditions": [],
  "trigger": [],
  "expectedResults": [],
  "actualResults": [],
  "recommendedLayer": "UNIT | API | INTEGRATION | UI | E2E | PERFORMANCE",
  "regressionTests": [],
  "missingInformation": [],
  "reviewRequired": true
}
```

### 생성 결과 검증 기준

AI가 생성한 테스트는 다음 조건을 통과해야 한다.

1. 문법·정적 분석 통과
2. 격리된 환경에서 실행 가능
3. 수정 전 버전에서 장애 재현
4. 수정 후 버전에서 성공
5. 다른 테스트와 실행 순서 독립
6. 운영 데이터 및 Secret 미사용
7. 고정 시간 대기 미사용
8. 핵심 결과의 명시적 Assertion 포함
9. 테스트 데이터 정리 가능
10. 동일 조건 반복 실행 시 안정적

### 안전장치

- 운영 로그에서 개인정보와 인증정보를 제거한다.
- 생성 코드는 네트워크가 차단된 Sandbox에서 실행한다.
- 운영 환경이나 운영 데이터에서 장애를 재현하지 않는다.
- 근본 원인이 확정되지 않으면 테스트를 생성하지 않는다.
- AI 생성 테스트는 반드시 사람의 리뷰를 거친다.
- 안정성 검증을 거치기 전에는 배포 차단 Suite에 등록하지 않는다.
- AI가 운영 코드를 직접 수정하거나 배포하지 못하게 한다.

### CI/CD 적용

장애 이슈 종료 조건에 회귀 테스트 연결 여부를 포함한다.

```text
근본 원인 확정
→ 수정 코드 반영
→ 장애 재현 테스트 작성
→ 수정 전 실패 확인
→ 수정 후 성공 확인
→ QA 리뷰 승인
→ 회귀 Suite 등록
```

테스트에는 장애 ID를 기록해 실패 시 어떤 장애가 재발할 가능성이 있는지 추적한다.

```python
@pytest.mark.incident("INC-2026-0142")
def test_only_one_order_succeeds_for_last_stock():
    ...
```

### 기대 효과 및 지표

- 장애 보고서와 회귀 테스트 간 추적성 확보
- 동일 원인의 운영 장애 재발 감소
- 장애 재현 및 테스트 설계 시간 단축
- 고객 영향 기반 자동화 우선순위 결정
- 장애 종료 후 테스트 작성까지 걸린 시간
- 운영 장애 대비 테스트 연결 비율
- 수정 전 장애 재현 성공률
- AI 생성 테스트의 QA 승인율과 Flaky 비율

### 설계 의도

운영 장애는 실제 고객과 비즈니스에 영향을 준 검증된 위험이므로 높은 자동화 ROI를 가진다. 다만 LLM이 장애 보고서를 잘못 해석하면 원인과 무관한 테스트를 생성할 수 있다.

따라서 근본 원인이 확정된 장애만 대상으로 하고, 수정 전 실패·수정 후 성공 검증과 QA 리뷰를 필수 단계로 둔다. AI는 장애 정보를 구조화하고 테스트 초안을 만드는 역할만 담당하며, 최종 레이어·우선순위·Assertion과 Suite 등록 여부는 QA가 결정한다.
